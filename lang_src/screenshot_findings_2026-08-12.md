# Находки со скриншотов пользователя (2026-08-12, вечер)

Контекст: пользователь считает, что "у нас ОГРОМНОЕ количество мест с откровенно
ХРЕНОВЫМ переводом" и подозревает архитектурную проблему, а не проблему промпта/Квена.
Задача — извлечь текст, задокументировать, где встретился, и передать на архитектурный
разбор.

## 1. "Невозможно выполнить" — составные строки (ПРИОРИТЕТ пользователя)

Скриншот: диалог взаимодействия "Удар: Обеденный стол" показывает:
```
Невозможно выполнить.  Missing item: Is Острый, Жёсткий, Ручной, Твёрдое, and Крепкий.
```
Смешение языков в одной строке: "Невозможно выполнить" переведено, "Missing item: Is"
осталось английским, а сам список ("Острый, Жёсткий, Ручной, Твёрдое, Крепкий") ПЕРЕВЕДЁН
корректно (это strNameFriendly отдельных condition-записей из нашего оверлея) — но
разделители между ними ", and " и обрамляющее "Is " не переведены.

**Корень найден в decompiled/CondTrigger.cs (свойство `RulesInfo`, ~строки 226-310):**
```csharp
StringBuilder stringBuilder = new StringBuilder();
if (bAND) {
    for (...) {
        if (i == 0) stringBuilder.Append("Is ");
        else if (i == последний) stringBuilder.Append(", and ");
        else stringBuilder.Append(", ");
        ...
        stringBuilder.Append(condition.strNameFriendly);  // <- ЭТО переводится нормально
    }
    ...
    stringBuilder.Append("Is NOT ");  // для aForbids
    ...
}
```
И decompiled/Interaction.cs (~строки 4430-4520), формирует сам "Missing item:":
```csharp
stringBuilder.Append(" Missing item: ");
stringBuilder.Append(value);           // <- список condition-имён, уже переведён
stringBuilder.Append(" Missing item x"); stringBuilder.Append(num2); stringBuilder.Append(": ");
stringBuilder.Append(" Room is ");
stringBuilder.Append(" 3rd party is ");
stringBuilder.Append(" Item present but, ");
stringBuilder.Append(" x Not Enough: ");
```
Все эти литералы ЕСТЬ в catalog/literals.json (Task 1/Фаза 1 их извлёк как candidate),
но НЕ утверждены — наш IL-транспайлер (LiteralPatcher.cs) патчит только прямые
`ldstr -> сеттер текста` вызовы, а не многошаговую конкатенацию через
`StringBuilder.Append` в цикле. Это ТА САМАЯ проблема "521 место композиции строк"
(patches/formats.md), которую предыдущая сессия сознательно отложила как отдельный
дизайн — теперь видно, что она даёт один из САМЫХ ЗАМЕТНЫХ игроку багов (сообщения
о невозможности выполнить действие — это КОНСТАНТНО видимый игроку UI).

## 2. "Ты сканируешь инвентарь X" — падеж (ИСПРАВЛЕНО в рамках этой сессии)

Скриншоты: "Ты сканируешь инвентарь стеллаж 1×1.", "Ты сканируешь инвентарь раковина."
EN источник: `[us] [scans] [them]'s inventory.` (interactions: `Inventory`,
`ACTInventoryPryAllow`, и похожие `GUITradeKiosk`, `GUIBulkTraderPodTrade` с `[browses]`).

Причина: движок при ПЕРВОМ упоминании сущности [them] всегда подставляет
`ent.CondOwner.ShortName` (сырое имя объекта, ТОЛЬКО именительный падеж) — это
происходит РАНЬШЕ проверки категории токена (subj/pos/obj), поэтому даже
`[them-pos]` не помог бы: первое упоминание объекта ВСЕГДА в именительном падеже,
а конструкция "инвентарь X" требует родительного ("инвентарь стеллажа").
Объектные короткие имена (ShortName) хранятся ТОЛЬКО в одной форме — падежных
вариантов для названий предметов/мебели в игре в принципе нет.

Временное исправление (в рамках сессии, не архитектурное): переформулировано как
"[us] [scans] инвентарь: [them]." (двоеточие вместо родительного падежа — обходит
грамматическую зависимость). Задеплоено для Inventory/ACTInventoryPryAllow/
GUITradeKiosk/GUIBulkTraderPodTrade.

**Это НЕ единичный случай** — любая фраза вида "[кого-то] X" (посессив от ПЕРВОГО
упоминания именованного объекта/NPC) в принципе не может быть грамматически
правильной без падежных форм ShortName, которых в данных игры нет. Возможных путей
для архитектурного разбора: (a) генерировать падежные формы через морфологический
анализатор на лету (pymorphy2-подобный) в самом плагине, (b) переформулировать ВСЕ
такие шаблоны в data/UI, избегая родительного падежа для первого упоминания —
系统ически, не точечно.

## 3. Крупные GUI-области, вообще НЕ покрытые переводом

Обнаружены в скриншотах целые панели интерфейса, которые остаются полностью или
почти полностью на английском — это НЕ баг качества перевода, а ПРОБЕЛ ПОКРЫТИЯ
(экстрактор/каталог префабов их не нашёл или не утвердил):

- **Экран создания персонажа (chargen)**: PRONOUN/HE-HIM/SHE-HER/THEY-THEM/
  FLIRTS WITH, и вся правая панель SKIN/HAIR/SCAR/GLASSES/BEARD/PUPILS/EYES/NOSE/
  TEETH/LIPS/NECK/HEAD/BODY — полностью английские. Это ИЗВЕСТНАЯ с самого начала
  проекта проблема (см. память: "Задача 0 (извлечение путей из префабов) — эти
  лейблы запечены в префабах, не проходят через обычный сцен-свип, экстрактор
  зависал на chargen-ассетах"). Судя по скриншоту — ДО СИХ ПОР не решена.
- **Crew Roster панель** (список смен экипажа): "Idle", "Hourly Status", "Free",
  "Sleep", "Work", "Permissions", "Disembark", "Open Airlocks", "Restore Parts",
  "Replace Batteries", "Replace Eva O2 Bottles", "Remove Helmet" — полностью
  английские.
- **Пульт дистанционной навигации (Remote Nav View / корабельная консоль)**:
  SHIP LABELS, TRACKING MODE, FOCUS, DIAGNOSTICS, PRINT STATUS, SHIP LOGS, MAP
  CONTROLS, WARNINGS (DOCK CLAMP/XPDR FAULT/ANT FAULT/TRACK WARN/PROX WARN),
  RESERVES (FUEL/POWER), TRANSPONDER/IFF, MANEUVER DRIVE (ROTORS/THROTTLE/YAW/
  STATION KEEPING/TRANSLATION/ZOOM), MOORING CONTROL — почти полностью английские
  (за вычетом нескольких переведённых фрагментов типа "1s"->"1s"/"RESET" не
  переведён вовсе). Огромная, часто используемая игроком панель.
- **ATC/Comms меню**: MAIN MENU, LOCAL CHANNEL, HAIL SHIP, MESSAGE LOG, DOCK INFO —
  английские; при этом соседний "Связь" (Comms Control) экран частично переведён,
  и там же —
- **Наложение текста (UI overflow)**: "< Запрос расписания...>" наложен на
  "< SOS Расписание рейсов >" —两 строки перекрывают друг друга. Это ИМЕННО детектор
  переполнения из Фазы 4 (QaMode overflow_report.tsv, 19 случаев были найдены ранее,
  но НЕ исправлены, только задетектированы). Русский текст физически не влезает в
  кнопку, рассчитанную на короткий английский лейбл.
- **Крыло "Задачи экипажа"**: "Status: Claimed by Chase Curry" — не переведено,
  видимо строка из другого места (не в нашем каталоге).
- **Spacebook (соцсеть NPC)**: "Заметки" переведены как заголовок колонки, но
  содержимое ("Became Biological Mother during: Your First Corporate Checkup") —
  английское; это, похоже, генерируемый lifeevent-текст, категория lifeevents НЕ
  подключена к ContentOverlay (проверено в прошлой сессии — lifeevents.json не имеет
  строковых полей в whitelist, только код-ссылки).
- **Патчноут "WELCOME TO OSTRANAUTS"**: полностью английский (New Plot and Endgames,
  Bounty System, ...) — вероятно низкий приоритет, это динамический контент патчей,
  обновляется при каждом релизе игры отдельно от статических данных.

## 4. Грамматическая корявость даже там, где ПЕРЕВЕДЕНО

Скриншот статус-сообщений чарджена (нижняя левая панель):
```
Ты не в форме: утомляемость от нагрузок выше, чем у большинства.
Ты имеешь плохие навыки пилотирования.
Ты имеешь постоянное нарушение зрения.
Ты с навыками проектирования, постройки и обслуживания космических кораблей.
Ты спец по передвижению и работе в невесомости.
```
"Ты имеешь X" — калька с английского "[us] [has] X", неидиоматично для описания
качеств/навыков (по-русски норма — "У тебя плохие навыки пилотирования", не "Ты
имеешь"). Это СИСТЕМНАЯ проблема токена `[has]`: он всегда конъюгируется как глагол
"иметь" ("[us] [has]" -> "Ты имеешь"), но для конструкций "[us] [has] skill/trait"
по-русски правильнее "У [us-obj] есть X" или просто "У [us] X" — это ТОТ ЖЕ класс
полисемии, что уже нашли для "[is]" (копула vs "находиться"): "[has]" тоже
полисемичен (обладание качеством vs владение предметом vs состояние).

## Вывод для архитектурного разбора

Как минимум ЧЕТЫРЕ независимых, но взаимоусиливающих класса проблем:
1. Композиция строк через StringBuilder (не покрыта транспайлером) — самый
   заметный игроку баг ("Невозможно выполнить" видно постоянно).
2. Падёж для первого упоминания именованных объектов (нет форм в данных).
3. Пробелы покрытия extraction — целые экраны/панели не в каталоге вообще
   (chargen labels, corabельные консоли, crew roster).
4. Полисемия токенов ([is], [has] и, вероятно, другие "вспомогательные" токены)
   ломает идиоматичность даже при 100% покрытии.

Мод сейчас построен как "патч поверх патча": Harmony IL-transpiler (Фаза 1) +
sweep/bind по путям иерархии (Фаза 2) + оверлей словарей по strName (Фаза 3) —
три РАЗНЫХ механизма для трёх разных источников текста, ни один явно не
проектировался с учётом СКЛОНЕНИЯ и КОМПОЗИЦИИ на уровне архитектуры (это были
"дожимы" по мере обнаружения багов). Пользователь прав, что стоит спросить: не
нужен ли принципиально иной подход (например: перехват на уровне финального
рендера текста в TMP_Text/UI.Text — единая точка правки ЛЮБОГО отображаемого
текста, независимо от источника, с морфологическим постпроцессингом) вместо
трёх параллельных систем экстракции/патчинга по источнику.
