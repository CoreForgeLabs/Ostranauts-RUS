## Task 8 — массовое утверждение и финальный прогон

**Найденная и исправленная проблема 1 — неоднозначные перегрузки методов.**
`MethodKey` (Task 2) строится по имени типа + имени метода + **количеству**
параметров, без учёта их типов. 5 методов в каталоге оказались перегрузками
с одинаковым числом параметров разных типов (напр. `RadialContextMenuObject.Setup`
имеет `Setup(Interaction)` и `Setup(CondOwner)` — оба схлопываются в `Setup/1`).
Решение для Фазы 1: такие methodKey **не утверждаются** (35 записей исключены из
approve) — по принципу деградации спеки: неоднозначный случай лучше пропустить,
чем рискнуть пропатчить не тот метод. Полноценное решение (расширить `MethodKey`
до полной сигнатуры параметров через `TypeReference.FullName`) — задача Фазы 2.

Один похожий случай (`Room::.ctor/1`, 2 записи) остался необработанным тем же
списком — обнаружен уже после финального прогона, попадает в тот же класс проблемы,
устраняется той же будущей доработкой `MethodKey`.

**Найденная и исправленная проблема 2 — коллизии генерируемых ключей.**
`MakeKey` не гарантировал уникальность: разные литералы в одном методе с одинаковым
`ordinal` (напр. `'N0'`/`'n0'`, регистронезависимая нормализация в `Slug`) и повторы
одного и того же литерала в одном методе (напр. `'UIPauseBtnIn'` — 9 раз в `CrewSim.Awake`)
давали одинаковый ключ. Итоговая формула разведения: `crc32(methodKey + '\0' + literal) +
'_' + ordinal` — оба компонента обязательны, каждый закрывает свой тип коллизии.

**Найденная и исправленная проблема 3 — `IL Compile Error` у 34 методов из 276.**
Транспайлер заменял одну IL-инструкцию (`ldstr`) на две, не перенося `labels`/`blocks`
(метки переходов и границы try/catch) со старой инструкции на новую. Если исходный
`ldstr` был целью `br`/`brtrue` или границей exception-блока, структура метода
ломалась и HarmonyX не мог собрать IL. Исправлено переносом через
`CodeInstruction.MoveLabelsFrom`/`MoveBlocksFrom` — после фикса все 34 метода
пропатчены штатно.

**Найденная и исправленная проблема 4 — экстракция брала все литералы метода,
не только текстовые (обнаружена пользователем в игре как `NullReferenceException`).**
Первый прогон (1735 записей, 276 методов) реально применился в игре и вызвал
`NullReferenceException` в `GUIChargenCareer.PageResume` / `PageBranchChoice` —
метод, ранее падавший с `IL Compile Error` (проблема 3), после фикса стал патчиться,
но один из утверждённых литералов внутри него оказался НЕ текстом, а частью логики
(условие/ключ ветвления), и его подмена сломала функциональность экрана, а не только
текст. Корень: экстракция (Task 3) брала любой `ldstr` в методе, содержащем где-либо
вызов text-sink — независимо от того, действительно ли этот конкретный литерал идёт
в текст. Пофикшено сужением: литерал становится кандидатом, только если он реально
достигает вызова `set_text`/`SetText` — напрямую (`ldstr; callvirt set_text`) либо
через одну промежуточную локальную переменную (`ldstr; stloc N; …; ldloc N; callvirt`).
Реализовано в `IsUsedAsSinkArgument` (`tools_cs/CatalogExtract/Program.cs`), с
`MethodBody.SimplifyMacros()` (пакет `Mono.Cecil.Rocks`) для явных индексов переменных.
Кандидатов в UI-текст упало с 1762 до 142 — подтверждает, что подавляющее большинство
прежних "кандидатов" были функциональными литералами, а не текстом.

Урок по критерию проверки: `grep -c "OUTPUTTING STACK TRACE"` в `Player.log` ловит
только полный краш процесса. `NullReferenceException` внутри UI-колбэка Unity
перехватывается движком и не роняет процесс — она видна только в `BepInEx/LogOutput.log`
как `[Exception]`. С этого момента проверка включает оба источника.

**Финальный прогон в игре (после всех четырёх фиксов):**

```
[Info   : OstraI18n] [i18n] каталог: утверждённых записей 141 в 60 методах
[Info   : OstraI18n] [i18n] литералы: методов пропатчено 60, подстановок 141, дрейф 0, методов не найдено 0
```

Крашей процесса нет, managed-исключений в логе плагина нет (`grep -c Exception` = 0).
Пользователь подтвердил в игре: ошибка в консоли (NullReferenceException) пропала.

Правка одной строки в `langs/ru/ui/generated.json` (`GUI_CHARGEN_AT_LARGE` →
`ПРОВЕРКА_ФАЙЛА`) технически подтверждена (значение читается из задеплоенного файла),
но не подтверждена визуально на выбранном тестовом персонаже — `"At Large"` показывается
только для персонажа без карьеры, а тестовый персонаж уже имел `Shipbreaker`. Тестовая
строка не входит в закоммиченный `langs/ru/ui/generated.json` (осталась только в
деплое как временная проверка).

**Найденная регрессия — текст, запечённый в префабах/сцене, перестал переводиться.**
Пользователь заметил на скриншоте, что `"Build-a-Resume Center"`, `"Career Summary"`,
`"DOCUMENTING CAREERS"` показываются по-английски, хотя раньше (до удаления `GuiText.cs`)
переводились. Проверено: этих строк нет ни в одном из 2708 извлечённых литералов —
значит это не хардкод в C#, а текст, запечённый в префабе/сцене (`m_text` компонента).
Старый механизм переводил такой текст через сканирование сцены + подмену по строке
(тот же механизм, что дал баг с `Tha`); новый IL-транспайлер покрывает только код.
Это ожидаемый пробел по границе Фазы 1 («Не входит: … Префабы и сцены — фаза 2»),
не новый баг — но пользователь не был предупреждён, что между фазами будет временный
откат уже переведённого префабного текста. Решение по согласованию с пользователем:
переходить к Фазе 2 (привязка по пути в иерархии для префабов) сразу, не откладывая.

Старый механизм (`GuiText.cs`, свип сцены, подмена по английскому тексту) удалён
полностью. `RuData.Load` больше не читает `gui.json`.
