## Task 8 — массовое утверждение и финальный прогон

**Найденная и исправленная проблема 1 — неоднозначные перегрузки методов.**
`MethodKey` (Task 2) строится по имени типа + имени метода + **количеству**
параметров, без учёта их типов. 5 методов в каталоге оказались перегрузками
с одинаковым числом параметров разных типов (напр. `RadialContextMenuObject.Setup`
имеет `Setup(Interaction)` и `Setup(CondOwner)` — оба схлопываются в `Setup/1`).
Решение для Фазы 1: такие methodKey **не утверждаются** (35 записей исключены из
approve) — по принципу деградации спеки: неоднозначный случай лучше пропустить,
чем рискнуть пропатчить не тот метод. Полноценное решение (расширить `MethodKey`
до полной сигнатуры параметров через `TypeReference.FullName`) — задача Фазы 2.

Один похожий случай (`Room::.ctor/1`, 2 записи) остался необработанным тем же
списком — обнаружен уже после финального прогона, попадает в тот же класс проблемы,
устраняется той же будущей доработкой `MethodKey`.

**Найденная и исправленная проблема 2 — коллизии генерируемых ключей.**
`MakeKey` не гарантировал уникальность: разные литералы в одном методе с одинаковым
`ordinal` (напр. `'N0'`/`'n0'`, регистронезависимая нормализация в `Slug`) и повторы
одного и того же литерала в одном методе (напр. `'UIPauseBtnIn'` — 9 раз в `CrewSim.Awake`)
давали одинаковый ключ. Итоговая формула разведения: `crc32(methodKey + '\0' + literal) +
'_' + ordinal` — оба компонента обязательны, каждый закрывает свой тип коллизии.

**Найденная и исправленная проблема 3 — `IL Compile Error` у 34 методов из 276.**
Транспайлер заменял одну IL-инструкцию (`ldstr`) на две, не перенося `labels`/`blocks`
(метки переходов и границы try/catch) со старой инструкции на новую. Если исходный
`ldstr` был целью `br`/`brtrue` или границей exception-блока, структура метода
ломалась и HarmonyX не мог собрать IL. Исправлено переносом через
`CodeInstruction.MoveLabelsFrom`/`MoveBlocksFrom` — после фикса все 34 метода
пропатчены штатно.

**Найденная и исправленная проблема 4 — экстракция брала все литералы метода,
не только текстовые (обнаружена пользователем в игре как `NullReferenceException`).**
Первый прогон (1735 записей, 276 методов) реально применился в игре и вызвал
`NullReferenceException` в `GUIChargenCareer.PageResume` / `PageBranchChoice` —
метод, ранее падавший с `IL Compile Error` (проблема 3), после фикса стал патчиться,
но один из утверждённых литералов внутри него оказался НЕ текстом, а частью логики
(условие/ключ ветвления), и его подмена сломала функциональность экрана, а не только
текст. Корень: экстракция (Task 3) брала любой `ldstr` в методе, содержащем где-либо
вызов text-sink — независимо от того, действительно ли этот конкретный литерал идёт
в текст. Пофикшено сужением: литерал становится кандидатом, только если он реально
достигает вызова `set_text`/`SetText` — напрямую (`ldstr; callvirt set_text`) либо
через одну промежуточную локальную переменную (`ldstr; stloc N; …; ldloc N; callvirt`).
Реализовано в `IsUsedAsSinkArgument` (`tools_cs/CatalogExtract/Program.cs`), с
`MethodBody.SimplifyMacros()` (пакет `Mono.Cecil.Rocks`) для явных индексов переменных.
Кандидатов в UI-текст упало с 1762 до 142 — подтверждает, что подавляющее большинство
прежних "кандидатов" были функциональными литералами, а не текстом.

Урок по критерию проверки: `grep -c "OUTPUTTING STACK TRACE"` в `Player.log` ловит
только полный краш процесса. `NullReferenceException` внутри UI-колбэка Unity
перехватывается движком и не роняет процесс — она видна только в `BepInEx/LogOutput.log`
как `[Exception]`. С этого момента проверка включает оба источника.

**Финальный прогон в игре (после всех четырёх фиксов):**

```
[Info   : OstraI18n] [i18n] каталог: утверждённых записей 141 в 60 методах
[Info   : OstraI18n] [i18n] литералы: методов пропатчено 60, подстановок 141, дрейф 0, методов не найдено 0
```

Крашей процесса нет, managed-исключений в логе плагина нет (`grep -c Exception` = 0).
Пользователь подтвердил в игре: ошибка в консоли (NullReferenceException) пропала.

Правка одной строки в `langs/ru/ui/generated.json` (`GUI_CHARGEN_AT_LARGE` →
`ПРОВЕРКА_ФАЙЛА`) технически подтверждена (значение читается из задеплоенного файла),
но не подтверждена визуально на выбранном тестовом персонаже — `"At Large"` показывается
только для персонажа без карьеры, а тестовый персонаж уже имел `Shipbreaker`. Тестовая
строка не входит в закоммиченный `langs/ru/ui/generated.json` (осталась только в
деплое как временная проверка).

**Найденная регрессия — текст, запечённый в префабах/сцене, перестал переводиться.**
Пользователь заметил на скриншоте, что `"Build-a-Resume Center"`, `"Career Summary"`,
`"DOCUMENTING CAREERS"` показываются по-английски, хотя раньше (до удаления `GuiText.cs`)
переводились. Проверено: этих строк нет ни в одном из 2708 извлечённых литералов —
значит это не хардкод в C#, а текст, запечённый в префабе/сцене (`m_text` компонента).
Старый механизм переводил такой текст через сканирование сцены + подмену по строке
(тот же механизм, что дал баг с `Tha`); новый IL-транспайлер покрывает только код.
Это ожидаемый пробел по границе Фазы 1 («Не входит: … Префабы и сцены — фаза 2»),
не новый баг — но пользователь не был предупреждён, что между фазами будет временный
откат уже переведённого префабного текста. Решение по согласованию с пользователем:
переходить к Фазе 2 (привязка по пути в иерархии для префабов) сразу, не откладывая.

Старый механизм (`GuiText.cs`, свип сцены, подмена по английскому тексту) удалён
полностью. `RuData.Load` больше не читает `gui.json`.

## Фаза 2 — привязка префабов/сцен по пути

**Task 2 (scene-срез).** Первая тестовая запись (`LoadingScreen/pnlEAMessage/txtFeedbackTitle`)
ни разу не сработала и не дала предупреждения — лог был полностью пуст по слову `slice`.
Причина: код молчал в случае `root == null` (сцена не содержит нужный корень), что
неотличимо от «ещё не сработало». После добавления лога даже для этого случая стало видно:
`LoadingScreen` — отдельная кратковременная сцена экрана загрузки, которая проходит до того,
как активная сцена становится доступной для проверки. Заменено на запись из `level2`
(`Canvas Stack/Canvas GUI/GUIZones/...`), подтверждённо принадлежащую активной игровой сцене —
привязалась с первой попытки. **Урок**: диагностический лог должен покрывать каждый исход
ветвления, а не только успех и один вид отказа — иначе "не сработало" и "ещё не произошло"
неразличимы.

**Task 4 (asset-срез, `GUISaveMenu/txtTitle`).** Компонент `LocalizedText` привязался без
ошибок, но видимый текст не изменился — заголовок остался `"Save Game"`. Причина: компонент
добавляется через поллинг уже к активному объекту (объект существовал до привязки), поэтому
`OnEnable` собственного скрипта объекта, устанавливающий `.text`, может выполниться в том же
кадре ПОСЛЕ нашего `OnEnable`, перезаписывая результат. Тот же класс проблемы, что привёл
к нестабильности старого движка (текст перезаписывается кем-то ещё), только источник другой —
не наш код гонится сам с собой, а с чужим `Start()`/`OnEnable()`. Исправлено повторным
применением в `LocalizedText` через `WaitForEndOfFrame`-корутину поверх немедленного вызова —
переживает гонку порядка инициализации в пределах одного кадра.

**Task 5 (массовое утверждение, глобальный `OnEnable`-хук).** Первый прогон после деплоя дал
серию `TypeLoadException: Could not resolve type... 'OstraI18n.Core.PathKey'` на каждый
`MaskableGraphic.OnEnable` в игре — это самый широкий по площади поражения баг за всю
разработку (хук глобальный, затрагивает весь UI). Причина не в логике: задеплоенный
`OstraI18n.Core.dll` был устаревшей сборкой без типа `PathKey` (8192 байт vs актуальных
8704) — при деплое Task 5 скопировали только `OstraI18n.dll`, забыв `OstraI18n.Core.dll`.
Динамический Harmony-патч резолвит типы из фактически загруженной сборки, а не из той,
с которой компилировался — рассинхронизация всплыла только в рантайме, а не при сборке.
После передеплоя обеих сборок — `0` исключений на чистом прогоне (125 записей: 121 scene,
46-23 объектов привязано по сценам). **Урок**: при деплое плагина с `ProjectReference` на
`Core` всегда копировать ОБЕ сборки заново, не полагаясь на то, что `Core.dll` "уже на месте" —
несоответствие версий даёт ошибку только в узком рантайм-пути (здесь — только когда
`AssetEntries.Count > 0` и хук реально патчится), а не при старте плагина.

Текст `"Save Game"` после исправления показывается непереведённым (плейсхолдер
`langs/ru/ui/prefabs.json` = копия английского, перевод — отдельная задача), но не пропал
и не превратился в мусор — это соответствует критерию готовности плана для ключей без
перевода. Оригинальная регрессировавшая строка `"Build-a-Resume Center"` не входит в область
Фазы 2 — это не литерал в коде и не текст в префабе, а вызов `DataHandler.GetString("GUI_CAREER_RESUME_TITLE")`,
переводимый отдельным более старым механизмом (`lang_ru/strings.json`, патч `DataHandler.GetString`
из `RuData`), не тронутым в этой фазе.

## Фаза 3 — контент-слой (оверлей по strName)

**Task 2 (импорт старого перевода).** Первый реальный прогон на категории `interactions`
(4900+ записей) сразу вскрыл два парсинг-бага, не проявлявшихся на тестовых данных:
старый перевод (`RUS_CoreForgeLabs/data/`) содержит файлы с UTF-8 BOM (`json.loads`
падал с `Unexpected UTF-8 BOM`), а часть текущих файлов игры содержит литеральные
control-символы внутри JSON-строк (`Invalid control character`, `strict json` их не
пропускает). Исправлено: `encoding="utf-8-sig"` при чтении + `json.loads(..., strict=False)`.
До исправления часть файлов молча пропускалась (`ПРОПУСК (bad JSON)`) — потеря не
привела к порче данных (значения просто не импортировались), но результат был неполным.

**Task 4 (визуальная проверка).** Строка `"permanent vision impairment"`
(`conditions/IsVisualImpaired.strDesc`) осталась английской в игре, несмотря на то что
оверлей содержит корректный перевод (`"[us] имеет постоянное нарушение зрения."`) и лог
подтверждает применение (`применено полей 12095, сирот 0`, без исключений). При этом
другие строки из того же прогона (`interactions/ACTBash.strTitle` → `"Удар"`,
`interactions/Inventory.strTitle` → `"Инвентарь"`) корректно показались в контекстном
меню объекта. Рабочая гипотеза: контекстное меню строится заново при каждом открытии
(читает `DataHandler.dictInteractions` вживую), а описание состояния персонажа, видимо,
кэшируется/копируется в объект `Condition` в момент применения состояния к персонажу —
если состояние было применено ДО того, как оверлей отработал (например, оно уже было
на персонаже на момент загрузки сейва, созданного раньше этого перевода), отображается
старое закэшированное значение. Требует подтверждения на новом сейве/новом применении
состояния после того, как оверлей уже загружен — не блокирует фазу, т.к. основной
механизм (мутация `DataHandler.dict*` по `strName`) подтверждён рабочим на свежем
контенте.

## Пост-Фаза 4 — динамически перезаписываемые плейсхолдеры в каталоге

Пользователь заметил под логотипом главного меню «Пример текста» вместо номера сборки
игры. Причина: каталог Фазы 2 извлекает текст из ПРЕФАБА (design-time снимок), но
`Root/Logo/txtVer` — не статичный текст, а плейсхолдер `"Sample text"`, который код игры
перезаписывает реальным значением при старте (`MainMenu.cs:407`, `component.text =
DataHandler.strBuild`). `LocalizedText` переприменяет перевод в конце кадра (фикс race
condition из Фазы 2 Task 4, придуманный для ПРОТИВОПОЛОЖНОЙ проблемы — чтобы наш перевод
не терялся под чужим `Start()`) — здесь та же механика работает во вред: наш перевод
побеждает и затирает динамический контент игры. Тот же класс бага нашёлся ещё в 12
записях (`prefabBinderTab*` вкладки `GUIManual.cs`, литерал `"Button"` — тоже
перезаписывается кодом из `strName` при инициализации).

**Урок**: правило утверждения «путь ≤3 сегмента» (консервативное сужение из плана
Фазы 2) снижает риск структурных коллизий, но не защищает от объектов, чей текст
ЛЕГИТИМНО перезаписывается кодом при каждом запуске — это ортогональная категория риска,
не связанная с длиной пути. Общий признак таких записей: подозрительно generic-литерал
(`"Sample text"`, `"Button"`, `"New Text"`, `"Placeholder"`) — при массовом утверждении
каталога такие литералы стоит проверять поиском по декомпиляту (`grep` по имени объекта/
родителя из пути) на предмет `.text = ` присваивания из кода до утверждения, а не
постфактум по жалобе пользователя.

Обе категории (13 записей) сняты с утверждения в `catalog/prefabs.json`
(`approved: false` + `rejectedReason`, не удалены — чтобы будущий аудит видел, что они
рассмотрены и отклонены осознанно) и убраны из `langs/{en,ru}/ui/prefabs.json`.
Привязка в `MainMenu2` упала с 23 до 10 объектов — ровно на 13, подтверждая, что все
отклонённые записи были живыми в этой сцене.
