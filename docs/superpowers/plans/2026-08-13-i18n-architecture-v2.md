# OstraI18n Архитектура v2 — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development` или `superpowers:executing-plans`. Шаги — чекбоксы (`- [ ]`). Фазы 5-9 выполняются строго по порядку; каждая имеет гейт, при провале которого следующая фаза не начинается.

**Goal:** Перевести мод с трёх параллельных механизмов извлечения/подмены (литералы / префабы / контент-оверлей) на слоистый конвейер `источник → шаблон/ключ → резолвер (падежи + морфология + предикаты) → безопасный failsafe на рендере → QA-отчёт`, закрыв четыре класса дефектов (композиция строк, падежи именованных сущностей, пробелы покрытия, полисемия служебных токенов) без остановки работающего мода и без единой строки кода, специфичной для русского языка.

**Tech Stack:** C# netstandard2.1, HarmonyX, BepInEx 6.0.0-be.785, TMPro (`ITextPreprocessor` подтверждён в `Unity.TextMeshPro.dll` игры), Python 3.14 + UnityPy 1.24.2 + TypeTreeGeneratorAPI.

# Часть A. Архитектурные решения

Ниже — решения, а не опции. Каждое обосновано фактами, добытыми из декомпилята и текущих данных в этой сессии. Будущим сессиям **не пересматривать** без нового факта, опровергающего основание.

## Р1. Композиция строк решается патчем метода-композитора, а не фрагментов

**Решение.** Ввести реестр `composers.json` в языковом пакете. Запись = один игровой метод, целиком собирающий отображаемый текст; Harmony-**префикс** полностью подменяет его реализацию, рендеря шаблон из пакета по структурированным входам самого метода. Единица перевода — шаблон с именованными плейсхолдерами и правилами склейки списков, не литерал-разделитель.

**Основание (проверено).** Два самых заметных игроку бага сводятся ровно к двум методам:

- `decompiled/CondTrigger.cs`, свойство-геттер `RulesInfo` (стр. 226+) — собирает `"Is A, B, and C."` из `aReqs`/`aForbids` + `DataHandler.GetCond(x).strNameFriendly` (последнее уже переведено оверлеем).
- `decompiled/Interaction.cs`, `FailReasons(bool bUsThem, bool bItems, bool bDebug)` (стр. 4400+) — собирает `" Missing item: "`, `" Room is "`, `" 3rd party is "`, `" x Not Enough: "` из приватного `mapFails` (`Dictionary<string, List<string>>`, стр. 217).
- Точка склейки, дающая скриншотную строку целиком: `decompiled/CondOwner.cs:3271` — `DataHandler.GetString("ERROR_CANT_DO_IA") + interaction.strTitle + ". " + interaction.FailReasons(...)`.

Оба метода имеют **структурированный вход** (массивы кодов условий, словарь причин) — значит шаблон можно отрендерить полностью на целевом языке, а не латать разделители. Расширение `LiteralPatcher` на `StringBuilder.Append` (178 мест) **отвергнуто**: транспайлер видит `ldstr`, но не видит ни порядок слов, ни падеж соседнего `strNameFriendly` — он физически не может дать «Требуется: острый, жёсткий и крепкий», только «Is острый, and жёсткий».

**Схема `composers.json`** (язык-агностична):

```json
{
  "CondTrigger.RulesInfo": {
    "requires": "Требуется: {list}.",
    "forbids":  "Не должно быть: {list}.",
    "list":     { "sep": ", ", "lastSep": " и ", "case": "nom" },
    "missing":  "ОТСУТСТВУЕТ: {code}"
  },
  "Interaction.FailReasons": {
    "us": " Мы: {v}", "them": " Цель: {v}", "room": " Помещение: {v}",
    "3rd": " Третья сторона: {v}",
    "items": " Не хватает: {v}", "itemsN": " Не хватает {n}\u00d7: {v}",
    "notEnough": " Недостаточно: {v}"
  }
}
```

Отсутствие ключа в `composers.json` = префикс не ставится, работает ванильный метод. Английский «пакет» шаблонов держится в `langs/en/composers.json` как эталон и как источник для диффа при патчах игры.

**Область.** Не «521 место» и не «700». Только методы, доказанно попадающие в UI, отранжированные инструментом Task 7.1. Ожидаемая цель фазы 7 — топ-12; остальное закрывает Р5.

## Р2. Падежи именованных сущностей — гибрид «таблица + правила», не морфологический анализатор

**Решение.** Три слоя, в порядке приоритета:

- **A. Таблица форм** в языковом пакете `named_forms.json`, ключ = `strName` записи `condowners` (стабильный игровой ID, не переведённый текст), значение = `{ "forms": {"nom":…,"gen":…,"dat":…,"acc":…,"ins":…,"prep":…}, "gender":"m|f|n", "animate":bool, "plural":bool }`.
- **B. Правило-генератор** `morph_rules.json` — упорядоченный список `{"match":"<regex по окончанию>","gender":…,"suffix":{"gen":"а","dat":"у",…}}`, применяемый к именам вне таблицы (процедурные имена кораблей, фамилии NPC, контент модов).
- **C. Фолбэк** — именительный падеж как сейчас, плюс запись в QA-отчёт `unresolved_forms.tsv`.

**Основание (замерено).** `langs/ru/data/condowners.json` — 1116 записей, из них 1058 имеют `strNameShort`, но **уникальных значений всего 338**. Полный порт pymorphy2 на C# ради 338 лемм — несоразмерная стоимость и новая ось хрупкости. 338 × 6 форм = ~2000 строк, генерируемых одним прогоном Qwen с валидацией — тот же конвейер, что уже отлажен в `tools/translate_data.py`.

**Обязательная правка кода** (иначе таблица бесполезна): `Patches.AttemptSubstitutionPrefix` и `AttemptProperNamePrefix` при первом упоминании (`!ent.named`) сейчас пишут `ent.CondOwner.ShortName` **игнорируя `tokenData.category`** (`plugin/OstraI18n/Patches.cs`, стр. 104-111 и 146). Нужно: спросить у резолвера форму для запрошенной категории, и только при её отсутствии — падать в `ShortName`. Это и есть «падежный слой между ShortName и предложением», которого нет.

**Отвергнуто:** «переформулировать все шаблоны, избегая косвенных падежей» как *единственный* путь — обходной приём `"[us] [scans] инвентарь: [them]."` работает, но он приносит канцелярит в каждую вторую фразу и не масштабируется на немецкий (4 падежа, обязательный артикль). Оставляем как тактику для строк, где таблица не помогает (несклоняемые/аббревиатурные имена).

## Р3. Пробелы покрытия — это отказ экстрактора `resources.assets`, а не отсутствие механизма

**Решение.** Чинить экстрактор (сменой стратегии обхода), а не менять `PrefabBinder`. Плюс отдельная ветка для MFD-экранов, которые вообще не префабные.

**Основание (замерено).** `catalog/prefabs.json` = 831 запись, разбивка по источникам: `level2` 549, `level0` 183, `level3` 76, `level1` 11, `level4` 4, `sharedassets0` 6, `sharedassets3` 2, **`resources.assets` — 0**. Проб: `PRONOUN`, `SKIN`, `HAIR`, `Idle`, `TRACKING MODE`, `HAIL SHIP`, `FOCUS`, `DIAGNOSTICS` — ни одного совпадения. То есть «целые экраны» не потеряны логикой привязки, они **никогда не были извлечены**: рантайм-механизм `asset`-привязки по пути (Фаза 2 Task 4/5) исправен и просто не имеет входных данных.

Причина отказа найдена в `tools/extract_prefab_paths_worker.py`: для **каждого** `MonoBehaviour` делается до трёх попыток `read_typetree(nodes=…)` с полными node-set'ами TMP. На 13173 объектах `resources.assets` это уходит в таймаут (8 воркеров × 30 мин → 8 записей).

**Новая стратегия обхода:** сначала прочитать все `MonoScript` файла (их сотни, не тысячи) и построить множество `PathID` скриптов `TMPro.TextMeshProUGUI`/`TextMeshPro`/`UnityEngine.UI.Text`; затем читать только базовый заголовок `MonoBehaviour` (`m_GameObject`, `m_Script` — фиксированный layout, typetree не нужен) и полный typetree парсить **только** для совпавших. Ожидаемое сокращение работы — на два порядка. Гейт Task 8.1 требует найти `PRONOUN` и `Hourly Status`; если и это не сработает — резервный путь: экспорт через AssetRipper/AssetStudio CLI в текстовый дамп и парсинг дампа (тот же выходной формат каталога, механизм привязки не меняется).

**Отдельная ветка — MFD (Remote Nav View / ATC).** Проверено: этот текст не в префабах и не литерал-в-сеттер, а литералы в структурах данных: `decompiled/Ostranauts.ShipGUIs.MFD/MFDMainMenu.cs` — `_leftDefault = { "<LOCAL CHANNEL", …, "<MESSAGE LOG" }`, `_rightDefault = { …, "HAIL SHIP>", … }`, `protected override string Title => "MAIN MENU"`. Все 18 страниц наследуют `MFDPage`, у которого есть **единственная точка выдачи** — `MFDPage.UpdateDisplay()`, упаковывающая `Title`/`Left`/`Right` в `MFDDTO` и шлющая в `GUIMFDDisplay.OnUpdateMFD`. Это семантический якорь: один Harmony-префикс на `MFDPage.UpdateDisplay` переводит `Title` и элементы `Left`/`Right` по словарю точного совпадения — и покрывает всю панель разом. Риск текста-как-ключа снимается тем, что перевод применяется к копии DTO, а не к полям страницы.

**Crew Roster** (`Idle`, `Hourly Status`, `Replace Batteries`…) в декомпиляте отсутствует → он в `resources.assets`, закрывается основным фиксом экстрактора.

## Р4. Полисемия `[is]`/`[has]` — шаблон, а не словарь; два механизма, оба в данных

**Решение.**

1. **Главный: перевод как шаблон целевого языка со свободным набором токенов.** Правило валидатора меняется с «набор токенов идентичен английскому» на «**каждый токен перевода разрешим**» (alias известен, категория есть в `DataHandler.categories`, глагол есть в `dictVerbs`). Тогда `"[us] [has] poor piloting"` переводится как `"У [us-obj] плохие навыки пилотирования."` — служебный токен просто исчезает, потому что в русском предикат выражается иначе. Это и есть «токен — предикат с валентностью, а не слово».
2. **Вспомогательный: смысловые псевдоглаголы, объявляемые пакетом.** `verbs.json` получает записи `is.cop`, `is.aux`, `has.obj`, `has.qual` с разными парадигмами; они регистрируются в `DataHandler.dictVerbs` из **постфикса `UnpackTokens`** (уже пропатчен — `plugin/OstraI18n/Patches.cs:UnpackTokensPostfix`). Проверено по `decompiled/DataHandler.cs`: `UnpackTokens()` вызывается на стр. 1157 **до** `PrepareConditionDescriptions()`/`PrepareInteractionInflections()` внутри того же `AllPostLoadAsync`, значит зарегистрированные там токены успевают попасть в разбор. Это даёт механическую массовую конверсию `[is]`→`[is.aux]` там, где реструктурировать фразу не надо.

**Основание.** `PrepareToken` (`DataHandler.cs:3121`) разбирает токен как `text.Split('-')` и проверяет каждую часть против `aliases` / `categories` / `dictVerbs` — то есть движок **уже** позволяет вводить любые новые категории и глаголы как данные. Неизвестный токен даёт `t.output == null` и **молча выбрасывается** (`Debug.LogWarning("token made without output")`) — отсюда обязательное требование: валидатор проверяет разрешимость **до** деплоя, а плагин на старте логирует список нерегистрированных токенов, встреченных в переводе.

**Бонус, найденный в декомпиляте и обязательный к использованию:** токен `custom` (`GrammarUtils.Custom`, стр. 409) уже умеет ветвиться по полу персонажа: `[<alias>-custom-characterGenderCond-<m>-<f>-<nb>]`. Это готовый, не требующий патчей движка способ согласования по роду в шаблонах — использовать вместо расширения таблиц там, где вариантов ровно три.

## Р5. Failsafe на рендере — ДА, но через `ITextPreprocessor`, а не через подмену `.text`

**Решение.** Добавить слой `RenderFallback`: реализация `TMPro.ITextPreprocessor`, назначаемая в свойство `TMP_Text.textPreprocessor` каждому TMP-компоненту через уже существующий и проверенный хук `MaskableGraphic.OnEnable` (`PrefabBinder`). Преобразование применяется **только к строке, идущей на построение меша**; свойство `.text` не изменяется никогда.

**Это и есть ответ на «ловушку текста-как-ключа»,** причём структурный, а не эвристический: игровой код, читающий `.text`, получает оригинал. Никакой реестр «дисплейный/недисплейный» не нужен, потому что подмена физически не наблюдаема из игрового кода.

**Основание (проверено).**
- В `F:\Games\...\Ostranauts_Data\Managed\Unity.TextMeshPro.dll` присутствуют символы `ITextPreprocessor`, `get_textPreprocessor`, `set_textPreprocessor`, `PreprocessText` — API доступен в этой версии.
- Игра сама `textPreprocessor` **не использует** (grep по всему `decompiled/` — 0 совпадений), слот свободен.
- Ловушка реальна и подтверждена: в декомпиляте **99 мест** читают `.text` обратно, среди них `Ostranauts.UI.CrewBar/GUICrewStatus.cs` (`if (_lblName.text != co.strName)`) и, что решает вопрос окончательно, `GUIChargenCareer.cs:612` — `if (rowBtn.GetComponentInChildren<TMP_Text>().text == "Take Ship")`, сравнение с английским литералом. Любой механизм, пишущий в `.text`, ломает эту ветку; препроцессор — нет.
- Legacy `UnityEngine.UI.Text` в игре практически не используется (0 файлов декомпилята против 259 с TMP) — failsafe сознательно TMP-only.

**Что делает слой:** (а) точное совпадение целой строки по словарю `ui/render_fallback.json` — безопасно воскрешает механизм «перевод по английскому тексту», удалённый в Фазе 1, потому что теперь он не может сломать логику; (б) якорные префиксные/regex-правила для остатка композиции (`^Missing item: ` и т.п.) как временная затычка до появления composer-патча. Кэш `original → result` обязателен (препроцессор вызывается на каждой регенерации меша), с отрицательным кэшированием промахов.

**Чем failsafe НЕ является:** не заменой слоёв выше. Строка, дошедшая до TMP, уже потеряла роли актантов и границы плейсхолдеров — падеж на этом уровне не чинится. Порядок приоритета жёсткий: composer/оверлей/ключ → и только необработанное попадает в fallback. QA-режим логирует всё, что было поймано fallback'ом, в `fallback_hits.tsv` — это рабочий список на «поднять уровнем выше».

## Р6. Устойчивость к патчам игры — по механизмам

| Механизм | Что хрупко сейчас | Что делаем |
|---|---|---|
| `LiteralPatcher` | `MethodKey` = тип+имя+**число** параметров (baseline.md: 5 перегрузок схлопнулись, 35 записей исключены); подстановка по `ordinal` при изменении порядка литералов даст чужой текст | Расширить `MethodKey` до полной сигнатуры (`TypeReference.FullName` параметров). Ввести обязательную **проверку дрейфа**: перед подстановкой сверять фактический литерал в IL с `literal` из каталога; несовпадение → пропуск + запись в `drift.tsv`, никогда не подстановка. Заморозить объём: новых утверждений не делать, механизм переведён в статус «legacy-мост», его записи постепенно мигрируют в composer/fallback. |
| `PrefabBinder` | Путь в иерархии — не стабильный ID; переименование объекта = молчаливый отказ | Стабильного asset-GUID в собранной игре нет (PathID пофайловый и меняется при пересборке) — путь остаётся. Компенсация: (1) хранить в записи **дополнительные якоря** — тип компонента и извлечённый `literal`; при промахе пути пробовать поиск по (родитель + literal) и **логировать как дрейф, не молча**; (2) `bind_report.tsv` с процентом разрешённых записей на запуск + порог: падение >5% относительно эталона = красный флаг в логе; (3) `tools/extract_prefab_paths.py` становится обязательным шагом «переиндексации» после каждого патча игры, с диффом каталога. |
| `ContentOverlay` | Хардкод `CategoryToField` (22 пары) — каждая новая категория требует правки кода; `TranslatableFields` — тоже код | Обе таблицы уезжают в `overlay_map.json` пакета. Плюс автодискавери: рефлексией перечислить публичные статические `Dictionary<string,*>` в `DataHandler`, сопоставить с папками, лишние/пропавшие вывести в лог. Точка привязки (префикс `AllPostLoadAsync`, до `UnpackTokens`/`Prepare*`) — **не трогать**, она выстрадана. Добавить счётчик-эталон: `Applied` ниже 90% от записанного в `baseline.json` → предупреждение в лог. |
| Патчи `GrammarUtils` | Поиск методов по имени | `TryPatch` уже логирует отказ; добавить агрегат «N patches ok, M failed» в **видимое** предупреждение при `M>0` (сейчас тонет в логе). |
| `RenderFallback` | Зависит от `ITextPreprocessor` | Публичный стабильный API TMP; при отсутствии — `null`-проверка и тихое отключение слоя. |

Общий принцип: **семантические якоря вместо порядковых**. `MFDPage.UpdateDisplay`, `Interaction.FailReasons`, `CondTrigger.RulesInfo`, `DataHandler.AllPostLoadAsync` — методы с осмысленным именем и ролью, переживающие рефакторинг тела; `ldstr #7 в методе X` — нет.

## Р7. Языковая нейтральность

`RuData` переименовывается в `LangPack` (класс, файл, все ссылки). Из кода уходят: `YouWord`-семантика (становится `pack.pronounOverrides`), знание имён падежей (пакет объявляет `"cases": ["nom","gen",…]`, код только передаёт строку категории), `Kind == "copula"`/`OmitPresent` остаётся, но это уже общелингвистическая абстракция, а не «русское». Раскладка пакетов унифицируется: сегодня их **две** (`langs/lang_ru/` для grammar/verbs/strings и `langs/ru/` для ui/data) — сливаются в `langs/<code>/` с манифестом `pack.json`. Автопроверка C2 (Task 5.6): grep по `plugin/` и `core/` на кириллицу вне комментариев и на литералы `"ru"`/`"Russian"` вне дефолтов конфига → 0.

Добавить второй язык = каталог + строка в `languages.json`. Приёмка этого решения — Task 9.4: собрать пустой `langs/de/` с 5 строками и убедиться, что игра стартует на немецком без правки кода.

## Р8. Что предложить разработчикам игры (north star)

Ключевое открытие сессии: **у игры уже есть работающая, ими же написанная конвенция локализации**, просто применённая к ~6 экранам из ~200. Найдено:

- `private void Localisation()` в `GUIOptions`, `GUIPDA`, `GUIFinance`, `GUIStationRefuel`, `GUITrade`, `GUICrewStatus` — метод, вызываемый из `PostInit`/`Awake`, который выставляет каждый лейбл через `((TMP_Text)x).SetText(DataHandler.GetString("GUI_..."))`.
- `DataHandler.GetString(string, bool allowEmpty)` (стр. 2173) + `dictStrings` (стр. 230), наполняемый из папки данных `strings/` через `LoadModJsons` + `ParseSimpleIntoStringDict` (стр. 993-1022).
- `Localisation.language` — статическое свойство, уже читаемое/пишущееся из `ConsoleResolver.cs:1188` и сохраняемое в `PlayerPrefs["Localisation"]`, но **ни на что не влияющее** (`Get()` просто возвращает `_language`).
- `JsonLocalisedStrings { strName, strLanguage, dict }` — DTO, соответствующее ровно тому формату, в котором наш мод уже держит `langs/*/ui/*.json`.
- `DataHandler.categories` / `dictVerbs` / `aliases` — грамматика уже целиком data-driven (`tokens/` папка).

Отсюда минимальный патч на их стороне — **пять пунктов, из которых три это загрузка данных**:

1. **Связать `Localisation.language` с загрузкой.** `LoadModJsons(strFolderPath + "strings/")` → сначала `strings/`, затем оверлеем `strings/<lang>/`; `GetString` получает цепочку fallback `<lang>` → English → `UNKNOWN_STRING`. Аналогично для оверлея переводимых полей контента: папка `data/<lang>/`, накладываемая **до** `UnpackTokens`/`Prepare*Inflections` (это ровно та точка, ошибка в которой уже стоила нам бага с сырыми токенами — сказать им это прямо).
2. **Компонент `LocalizedLabel : MonoBehaviour { public string Key; }`**, проставляемый в префабах на этапе авторинга, и его применение в `OnEnable`. Это тот самый «инъекционный слой на уровне сборки префабов», которого просит архитектурный разбор. **Наш `catalog/prefabs.json` — готовый поимённый worklist**, что именно проставить: путь → предлагаемый ключ → текущий английский текст.
3. **Довести конвенцию `Localisation()` до остальных экранов**, заменив литералы. Наш `catalog/literals.json` (2708 записей, 168 утверждённых) — исходный список кандидатов с уже сгенерированными ключами.
4. **Композиторы: `GetString` + хелпер списков.** Заменить в `CondTrigger.RulesInfo` / `Interaction.FailReasons` / `MFDPage`-наследниках жёсткие фрагменты на `string.Format(DataHandler.GetString("CT_RULES_REQUIRES"), DataHandler.FormatList(items))`, где `FormatList` берёт разделители из строк локализации. Наш `composers.json` — готовая спецификация того, какие шаблоны нужны.
5. **`ShortName` с падежом.** Добавить `CondOwner.ShortNameFor(string form)` со значением по умолчанию `=> ShortName`, консультирующийся с загруженной из данных таблицей форм; `GrammarUtils.AttemptSubstitution`/`AttemptProperName` передают туда `tokenData.category`. Одна виртуальная точка расширения снимает целый класс невозможных переводов для всех флективных языков (славянские, финно-угорские, немецкий).

Сверх кода отдаём: инструменты покрытия (`coverage_report.tsv`), детектор переполнения (`overflow_report.tsv`), псевдоязык (`QaMode`), экстракторы. Формулировка предложения: **мы не просим движок локализации — мы просим достроить тот, который у вас уже начат, и приносим данные и инструменты.**

## Р9. Разногласия источников — разрешение

- Аудит (`docs/architecture-audit.md`) утверждает «ни один пробел не требует смены архитектуры»; qwen-разбор — «три механизма не годятся как архитектура». **Разрешено в пользу аудита по фактам, но с оговоркой qwen по составу.** Замер показал: пробел покрытия — отказ *экстрактора* (0 записей из `resources.assets`), а не порочность привязки по пути. Механизмы `PrefabBinder` и `ContentOverlay` сохраняются. Прав qwen в одном: `LiteralPatcher` — тупик (замораживаем, не расширяем) и «единица перевода — шаблон» (принято как Р1).
- qwen предлагает единый перехват как «страховочный слой», не решая ловушку текста-как-ключа (только называет её). **Решено конкретно (Р5): `ITextPreprocessor`**, ловушка снимается структурно; эвристика «дисплейный/недисплейный текст» не нужна и не вводится.
- qwen: «морфологический движок — правильный долгосрочный путь». **Отвергнуто** количественным аргументом: 338 уникальных лемм (Р2).
- Скриншотный отчёт предлагает вариант (b) «переформулировать все шаблоны». **Понижено до тактики**, не стратегии (Р2).

## Краткое резюме принятых решений

**1. Композиция.** Не расширять IL-транспайлер на `StringBuilder`. Патчить методы-композиторы целиком, рендеря шаблон из `composers.json`. Обе скриншотные болячки — это ровно два метода: `CondTrigger.RulesInfo` и `Interaction.FailReasons` (у обоих структурированный вход: массивы кодов условий и приватный `mapFails`), склеиваемые в `CondOwner.cs:3271`.

**2. Падежи имён.** Гибрид, не морфоанализатор: замерено — уникальных `strNameShort` всего **338**, поэтому таблица форм в пакете + правило-генератор по окончаниям + фолбэк. Требует малой правки `Patches.cs`: при первом упоминании сущности код сегодня игнорирует `tokenData.category`.

**3. Покрытие.** Механизм привязки исправен — отказал экстрактор: в каталоге **0 записей из `resources.assets`** при 13173 объектах. Чиним стратегию обхода (фильтр по `MonoScript` вместо перебора typetree). MFD-панели (Nav/ATC) — отдельный случай: не префабы, а литералы в `List<string>`, покрываются одним префиксом на семантический якорь `MFDPage.UpdateDisplay`.

**4. Полисемия `[is]`/`[has]`.** Правило валидатора меняется с «токены идентичны английским» на «каждый токен разрешим» — тогда `[has]` просто исчезает в пользу «У [us-obj] …». Дополнительно — смысловые псевдоглаголы `is.cop`/`is.aux`/`has.obj`/`has.qual`, регистрируемые из данных (движок это позволяет: `PrepareToken` — обычный `Split('-')` по data-driven спискам).

**5. Failsafe — да, но через `ITextPreprocessor`.** API подтверждён в игровой `Unity.TextMeshPro.dll` и игрой не занят. Преобразование применяется только к строке для меша, `.text` не меняется — ловушка «текст как ключ» снимается структурно, а не эвристикой. Это критично: в декомпиляте **99** обратных чтений `.text`, включая `GUIChargenCareer.cs:612` — сравнение с литералом `"Take Ship"`.

**6. Разногласие двух документов** разрешено фактами: аудит прав («архитектуру менять не надо»), qwen прав в частности («`LiteralPatcher` — тупик, единица перевода — шаблон»).

**7. Языковая нейтральность:** `RuData` → `LangPack`, слияние двух раскладок пакета в одну, все падежи/карты/шаблоны — данные; приёмка = запуск на немецком без правок кода.

**8. Разработчикам** предлагается не новый движок, а достройка их собственного: у них уже есть `Localisation()`-конвенция в 6 GUI-классах, `DataHandler.GetString`, `dictStrings` из папки `strings/`, неиспользуемый `Localisation.language` и data-driven токены. Минимальный патч — 5 пунктов, 3 из них про загрузку данных; наши каталоги — готовый worklist.

**9. Миграция** — 5 фаз с гейтами; данные перевода (24861 поле + UI-словари + каталог префабов) переиспользуются 1:1, схема ключей заморожена; Фаза 5 обязана дать побайтово тот же лог, что и сегодня.
