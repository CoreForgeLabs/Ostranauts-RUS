# OstraI18n — key-based i18n для Ostranauts

**Дата:** 2026-08-11
**Статус:** дизайн утверждён, план реализации не написан

## Цель

Полноценная поддержка мультиязычности в Ostranauts, пригодная для передачи разработчикам
игры и внедрения в саму игру. Весь отображаемый текст должен храниться в файлах и
редактироваться без правки кода. Добавление нового языка — копирование папки и одна
строка в манифесте.

Перевод на русский — доказательство работоспособности системы, а не самоцель.

## Почему переписываем

Текущая реализация подменяет текст **в момент отображения**, используя **английский текст
как ключ** (`GuiText.Translate`: строка на экране ищется в словаре и заменяется). Это
подход XUnity.AutoTranslator — слой поверх игры.

Такой ключ порождает неустранимый класс багов:

| Симптом | Причина |
|---|---|
| `HOME` в сайдбаре и `HOME` в другом окне переводятся одинаково | ключ не различает контекст |
| Обрывок `Tha` из анимации печати попал в словарь и сломал заголовок | кадр анимации неотличим от готовой строки |
| Короткие слова (`M`, `OR`, `ALL`) конфликтуют между экранами | глобальное пространство совпадений |
| Динамический текст (`Chase Curry, Captain`) не переводится | склеенную строку нельзя разобрать обратно |

Костыли против этих багов (guard от печатной машинки, вариантные карты, фильтры мусора)
лечат симптомы. Класс задач устраняется только сменой ключа.

Дополнительно: артефакт такого перевода (словарь «английский → русский») **невозможно
передать разработчикам** — им нужны ключи, а не текстовые пары.

## Что уже есть в игре

Разработчики заложили каркас i18n и не дописали его:

| Элемент | Состояние |
|---|---|
| `Localisation.Get()` | заглушка, всегда возвращает `"English"` |
| `JsonLocalisedStrings { strName, strLanguage, dict }` | класс объявлен, **нигде не читается** |
| `JsonLocalisedStringsRaw { strName, strLanguage, aValues[] }` | то же |
| `DataHandler.GetString(key)` → `dictStrings` | **работает правильно**, 1179 ключей |
| Консольная команда `language` | принимает English/Portuguese, пишет в PlayerPrefs |
| `tokens/grammar.json` с полем `"lang": "eng"` | формат под языковые пакеты, код его игнорирует |

Мы не изобретаем новую систему — мы достраиваем начатую.

## Инвентаризация текста

Замеры по декомпиляту (`decompiled/`, 1329 файлов C#) и по ассетам (UnityPy + TypeTreeGenerator).

#### Префабы: шаблоны против экземпляров сцены

Распределение по источникам извлечения принципиально для дизайна привязки:

Реальный объём меньше прежней оценки в четыре раза и полностью выполним имеющимся

## Архитектура

Принцип: **перехват в месте хранения текста, а не в момент отображения.**

| Где лежит текст | Механизм | Матчинг по английскому тексту |
|---|---|---|
| `strings.json` | загрузка языкового пакета в `dictStrings` | нет |
| Литерал в сборке (`ldstr`) | IL-транспайлер → `I18n.Get(ключ)` | нет |
| Префаб/сцена (`m_text`) | привязка по пути в иерархии | нет (путь, не текст) |
| Контент-данные | оверлей по `strName` | нет |

Сопоставления по английскому тексту не остаётся **нигде**.

### IL-транспайлер — ядро подхода

В IL хардкод-литерал — одна инструкция:

```
ldstr "POINTS LEFT"
```

Транспайлер заменяет её на:

```
ldstr "GUI_CHARGEN_POINTS_LEFT"
call  I18n.Get(string)
```

Что эквивалентно правке в исходнике, которую предстоит сделать разработчикам:

```csharp
- txt.text = "POINTS LEFT";
+ txt.text = GetString("GUI_CHARGEN_POINTS_LEFT");
```

Мод выполняет механически ту же трансформацию, что разработчик сделает руками. Отсюда
соответствие 1:1: каталог литералов **является** списком правок, а мод — доказательством,
что каждая правка работает.

**Следствия:**

1. Не важно, как текст попадает на экран: `.text`, `SetText()`, конкатенация, многоэтапная
   сборка тултипа. Перехват в источнике покрывает все пути, включая 182 вызова `SetText`.
2. Вариантные карты (`Buy`/`Sell` по одному пути) не нужны: это два разных `ldstr`,
   каждый получает свой ключ автоматически.
3. Проблема кадров анимации печати перестаёт существовать как понятие.

**Безопасность по умолчанию:** транспайлер подменяет только литералы, у которых есть
одобренная запись в каталоге. Незнакомый литерал проходит нетронутым.

#### Идентификация литерала

Порядковый номер `ldstr` в методе **непригоден как ключ**: разработчик добавляет
`Debug.Log("x")` в начало метода — все последующие индексы смещаются, и каждый ключ
начинает показывать чужую строку. Молча, без падения.

Литерал идентифицируется тройкой:

```
(полное имя метода, значение литерала, номер среди одинаковых значений в этом методе)
```

| Событие | Поведение |
|---|---|
| вставлен новый литерал в метод | ключи не задеты — привязка по значению, не по позиции |
| текст литерала изменён разработчиком | значение не найдено → подстановка отключается, ключ в отчёт о дрейфе |
| метод переименован | все его ключи в отчёт о дрейфе |
| один литерал дважды в методе | различаются номером среди одинаковых |

Изменение текста — единственный случай, ломающий привязку, и это именно тот случай,
когда перевод в любом случае требует пересмотра. Ошибка при этом громкая, а не тихая.

#### Общие ключи для повторяющихся литералов

`"Cancel"` встречается во множестве мест. Ключ на каждое место означает раздутый каталог
и одно слово, показанное переводчику десятки раз.

Правило: литерал получает **общий ключ** (`GUI_COMMON_CANCEL`), если входит в
курируемый словарь типовых элементов интерфейса (Cancel, OK, Close, Back, Yes, No,
Confirm, Save, Load, Delete, Apply, Reset). Остальные повторы сохраняют ключ на место —
одинаковый английский текст в разном контексте может требовать разного перевода.

Словарь типовых элементов ведётся вручную и мал по определению; всё, что в него не входит,
по умолчанию получает ключ на место. Это безопасная сторона ошибки: лишний ключ лечится
объединением, ошибочно объединённые ключи дают неверный перевод в игре.

## Классификация динамического текста

«Динамический» — не одна категория. Способ починки определяется причиной изменчивости.

| Вид | Пример | Мест | Решение | Покрытие модом |
|---|---|---|---|---|
| **A. Проброс данных** | `.text = item.strName` | ~570 | перевод контент-слоя | полное |
| **B. Метка + значение** | `name + " of the " + ship` | ~270 | формат-строка `{0} с корабля {1}` | частичное |
| **C. Чистый литерал** | `.text = "POINTS LEFT"` | 296 | ключ + `GetString` | полное |
| **D. Настоящие данные** | `01:23.12`, `3,698 MB` | — | локализация форматов чисел/дат | вне v1 |

**Вид B — единственное, что требует правки кода игры.** Конкатенацию нельзя починить на
уровне отображения: в русском другой порядок слов и падеж (`"Чейз Карри с корабля «Мул»"`).
Разбирать склеенную строку обратно — это возврат к regex.

Частично B решается транспайлером даром: перевод литерала-связки сохраняет слоты на местах
(`" of the "` → `" с корабля "`). Формат-строки нужны только там, где меняется порядок слов.

Промежуточное состояние наблюдаемо и измеримо. Строка `Chase Curry, Captain, Active Shift: Work`
после перевода контента (A) но до формат-строк (B) выглядит как
`Chase Curry, Капитан, Active Shift: Работа` — английскими остаются ровно хардкод-связки,
что позволяет отсортировать их по частоте и патчить сверху вниз.

## Структура файлов

Разделение: **где лежит текст** (не зависит от языка) и **что он говорит** (зависит).

```
BepInEx/plugins/OstraI18n/
├── config.json                  выбранный язык, флаги
├── catalog/                     ГДЕ. Один на все языки.
│   ├── literals.json            ключ → {метод, индекс ldstr, англ. оригинал}
│   ├── prefabs.json             ключ → {путь в иерархии, англ. оригинал}
│   ├── formats.json             места композиции → предлагаемая формат-строка
│   └── content.json             файл+strName → переводимые поля
└── langs/                       ЧТО. По папке на язык.
    ├── languages.json           манифест
    ├── en/
    ├── ru/
    │   ├── meta.json
    │   ├── ui/                  строки по экранам
    │   │   ├── common.json  chargen.json  shipedit.json  nav.json
    │   │   └── pda.json  trade.json  tutorial.json  settings.json
    │   ├── grammar.json         местоимения
    │   ├── verbs.json           спряжения
    │   └── data/                контент, зеркалит StreamingAssets/data
    └── de/
```

`catalog/` вынесен из `langs/`: «в этом методе на позиции 3 лежит UI-строка» — факт об
**игре**, не о языке. Внутри языковой папки он дублировался бы на каждый язык и расходился.

UI разбит по экранам: 2600 ключей в одном файле дают конфликты в git при параллельной
работе переводчиков. Уникальность между файлами гарантируется префиксом и проверяется
валидатором.

### Формат файла строк

Используется формат, объявленный в игре классом `JsonLocalisedStrings`, но не читаемый ею:

```json
[{
  "strName": "Game Strings",
  "strLanguage": "Russian",
  "dict": {
    "GUI_TRADE_BUY": "Купить",
    "GUI_SAVE_PLAYER_OF_SHIP": "{0} с корабля {1}"
  }
}]
```

Форма `dict` предпочтена плоскому `aValues` (чередование ключ-значение): сбой на один
элемент ломает весь файл.

### Множественные числа

Английский имеет две формы (`1 item` / `2 items`), русский — три
(`1 предмет` / `2 предмета` / `5 предметов`), другие языки — от одной до шести.
Конкатенация числа со строкой корректный перевод не даёт, поэтому значение ключа может
быть не строкой, а набором форм по категориям CLDR:

```json
{
  "GUI_INVENTORY_ITEMS": {
    "one":   "{0} предмет",
    "few":   "{0} предмета",
    "many":  "{0} предметов",
    "other": "{0} предмета"
  }
}
```

Правило выбора категории объявляется в `meta.json` языка, а не зашивается в код:

```json
{
  "pluralRule": "n%10==1 && n%100!=11 ? 'one' : n%10>=2 && n%10<=4 && (n%100<12 || n%100>14) ? 'few' : 'many'"
}
```

Вызов: `I18n.Plural(key, count, args)`. Английский пакет объявляет две категории
(`one`/`other`), русский — три, добавление языка с иным правилом не требует правки кода.

Кандидаты на плюрализацию выявляются при извлечении каталога: места, где в строку
подставляется числовое значение, помечаются флагом `plural: candidate` и вычитываются
человеком — автоматически отличить «5 предметов» от «версия 5» нельзя.

### Схема ключей

```
GUI_<ЭКРАН>_<ЭЛЕМЕНТ>[_<УТОЧНЕНИЕ>]

GUI_CHARGEN_POINTS_LEFT
GUI_SHIPEDIT_BTN_REPLACE_FLOORS
GUI_TRADE_BUY
```

Совпадает с существующими 1179 ключами игры (`GUI_QUIT_CONFIRM`) — единое пространство имён.
Генерируется автоматически из имени класса и переменной, вычитывается человеком.

### `meta.json`

```json
{
  "code": "ru",
  "name": "Русский",
  "nameEnglish": "Russian",
  "fallback": ["en"],
  "completeness": { "ui": 0.98, "content": 0.35 }
}
```

Добавление языка: скопировать `langs/en/` → перевести → дописать строку в `languages.json`.
Без правки кода и пересборки плагина. Отсутствующий ключ уходит по цепочке `fallback`,
никогда не показывая `UNKNOWN_STRING`; частично переведённый язык играбелен.

## Рантайм-компоненты

```
   catalog/ ──────► Catalog ──────┐
                                  ▼
   langs/<lang>/ ──────────►  I18n (Get, Format, SetLanguage, OnLanguageChanged)
                                  │
        ┌─────────────────┬───────┴────────┬──────────────────┐
        ▼                 ▼                ▼                  ▼
  LiteralPatcher    StringsLoader    PrefabBinder      ContentOverlay
  ldstr → ключ      dictStrings      LocalizedText     data/ по strName
```

| Компонент | Задача |
|---|---|
| `I18n` | единственная точка входа: `Get(key)`, `Format(key, args)`, `SetLanguage`, событие смены |
| `Catalog` | читает `catalog/*.json`, знает соответствие метод+индекс → ключ и путь → ключ |
| `LiteralPatcher` | вешает Harmony-транспайлер на методы с одобренными литералами |
| `StringsLoader` | заполняет `dictStrings` из `langs/<активный>/ui/*.json` |
| `PrefabBinder` | по списку путей из каталога вешает `LocalizedText` на найденные объекты |
| `LocalizedText` | компонент с ключом; ставит текст в `OnEnable`, реагирует на смену языка |
| `ContentOverlay` | накладывает `langs/<lang>/data/` на игровые данные по паре файл+`strName` |

`LocalizedText` — тот же компонент, который разработчики повесят в редакторе. Мод вешает
его в рантайме; исходник уезжает разработчикам без изменений.

`DataHandler.GetString` **не патчится**. Патчится загрузка строк — то, что сделали бы
разработчики: не перехват каждого вызова, а загрузка нужного файла.

### Привязка префабов

2636 из 3459 найденных текстовых объектов лежат в префаб-шаблонах, а не в сценах.
Абсолютный путь в иерархии для них не существует: в рантайме шаблон инстанцируется как
`prefabBtnQuickAction(Clone)` под произвольным родителем, в произвольном количестве копий.

Поэтому каталог различает два вида привязки:

```json
{
  "GUI_ZONES_DESCRIPTION": {
    "kind": "scene",
    "path": "Canvas Stack/Canvas GUI/GUIZones/Scrollview/TitleContainer/DescriptionLabel"
  },
  "GUI_QUICKBAR_ACTIONS": {
    "kind": "asset",
    "prefab": "prefabBtnQuickAction",
    "path": "txt"
  }
}
```

**`scene`** — объект существует в сцене, ищется по абсолютному пути при загрузке сцены.

**`asset`** — объект принадлежит префаб-шаблону. Шаблон находится через
`Resources.FindObjectsOfTypeAll`, возвращающий загруженные ассеты, включая не находящиеся
в сцене. `LocalizedText` вешается **на шаблон**, и все создаваемые копии наследуют его
автоматически — вместо погони за каждым клоном в рантайме.

Это же поведение переносится к разработчикам буквально: в редакторе компонент вешается
на префаб, а не на его экземпляры.

### Шрифты

Кириллица покрывается подсадкой `NotoSansGC-Regular SDF` в глобальный fallback TMP.
Для произвольного набора языков это не масштабируется: CJK, арабский, иврит требуют
своих начертаний.

Шрифтовая цепочка объявляется в `meta.json` языка и применяется при переключении:

```json
{ "fontFallbacks": ["NotoSansGC-Regular SDF", "NotoSansSC-Regular SDF"] }
```

Отсутствующий в сборке шрифт даёт предупреждение и пропускается, а не ломает рендер.

### Удаляется из текущего плагина

`GuiText.Translate`, глобальный словарь по английскому тексту, свип сцены каждые 2 секунды,
guard от анимации печати, вариантные карты, дамп `gui_unknown.txt` в продакшене.
Механизмы не чинятся — исчезает класс задач, который они обслуживали.

Дамп-режим сохраняется как **инструмент авторинга** (сбор каталога), но выключен в релизе.

### Смена языка без перезапуска

| Слой | Мгновенно |
|---|---|
| UI-строки (`GetString`, префабы) | да, через `OnLanguageChanged` |
| Литералы в коде | да, транспайлер зовёт `I18n.Get` при каждом вызове |
| Контент (предметы, диалоги) | нет, нужен перезапуск — данные разбираются при загрузке |

### Деградация

Принцип: **плагин не может сделать игру хуже, чем без него.** Любой сбой откатывается к
ванильному английскому.

| Сбой | Поведение |
|---|---|
| нет ключа в языке | fallback-цепочка → английский → сам ключ |
| литерал изменился после апдейта игры | подстановка пропускается, предупреждение |
| исключение в транспайлере метода | метод остаётся ванильным, остальные патчатся |
| нет папки языка / битый JSON | английский, предупреждение |

### Переживание обновлений игры

При старте `Catalog` сверяет ожидаемый английский оригинал с фактическим содержимым сборки.
Расхождение отключает подстановку точечно и пишет список разошедшихся ключей — задание на
переизвлечение каталога. (Игра обновилась во время разработки дизайна; механизм проверен
как необходимый, а не гипотетический.)

### QA: псевдоязык

Псевдо-язык `qa` оборачивает каждую строку маркерами:

```
⟦Купить⟧      прошло через систему
Buy           не прошло, текст всё ещё захардкожен
```

Позволяет за один взгляд на экран увидеть непокрытые места вместо ручного сличения скриншотов.

### Раздувание текста и вёрстка

Русский текст длиннее английского на 15–30%, немецкий — до 40%. Элементы интерфейса
свёрстаны под английскую длину, поэтому перевод физически не помещается.

Проблема уже наблюдается: в списке целей обучения `Обучение: Управление временем`
налезает на соседний пункт, потому что элемент рассчитан под `Tutorial: Time Controls`.
Это не потенциальный риск, а текущий дефект.

Три меры:

**1. Детектор переполнения в QA-режиме.** TMP позволяет сравнить требуемый размер текста
с размером контейнера. В режиме `qa` каждый переполненный элемент пишется в отчёт с ключом
и путём. Это даёт точный список проблемных мест вместо разглядывания скриншотов.

**2. Ограничение длины в каталоге.** Ключи, привязанные к элементам фиксированной ширины,
получают поле `maxLen`. Заполняется по мере обнаружения детектором, проверяется валидатором:
перевод длиннее лимита не проходит сборку.

**3. Предупреждение на непропорциональный рост.** Валидатор помечает переводы коротких строк
(до 20 символов — как правило, кнопки), выросшие более чем в полтора раза. Не блокирует,
но выносит на вычитку: для кнопки обычно существует более короткий вариант.

Автоматическое масштабирование шрифта глобально не включается: оно ломает единообразие
интерфейса и маскирует проблему вместо её решения.

## Контент-слой

### Оверлей по идентификатору, а не копии файлов

**Идентификатором записи служит поле `strName`.** Вопреки названию, это не отображаемый
текст, а внутренний ID (`ACTAddConnection`, `FloorGrate01Install`). Отображаемый текст
лежит в `strDesc`, `strTitle`, `strTooltip`, `strNameFriendly`, `strNameShort`,
`strFriendlyName`. Проверено: **0 записей из 12 800 не имеют `strName`**.

`strName` уникален внутри файла (4 исключения на 12 800), но **135 идентификаторов
встречаются более чем в одном файле**, поэтому ключ оверлея — пара «относительный путь
файла + `strName`». Плоский словарь по одному `strName` дал бы коллизии.

Хранятся только переводимые поля:

```json
{
  "interactions/interactions.json": {
    "ACTAddConnection": {
      "strTitle": "Добавить связь",
      "strDesc":  "[us] [adds] связь с [them]"
    }
  },
  "installables/installables.json": {
    "FloorGrate01Install": { "strTooltip": "Устанавливает предмет." }
  }
}
```

Поле `strName` в оверлее никогда не пишется — его изменение сломало бы ссылочную
целостность данных игры.

| Событие | Копии файлов (старый подход) | Оверлей по `strName` |
|---|---|---|
| игра добавила предмет | не виден | показан по-английски, перевод дописывается |
| игра изменила предмет | молча перезаписан старым | расхождение видно |
| игра удалила предмет | мусор навсегда | валидатор помечает сироту |
| размер | 8+ МБ дублей | только переводы |

### Импорт старого перевода

Старый перевод (`Ostranauts/old/`) содержит полные переведённые копии и был получен
regex-заменами, что дало порчу строк. Импорт ведётся **только по идентификатору**:

1. Из старой копии: `strName` → переведённые поля
2. Из текущего файла игры: `strName` → английский оригинал
3. Совпал `strName` в том же файле — берётся перевод. Сопоставления по тексту нет нигде.
4. Валидация каждой строки: токены `[us]`/`[them]`, плейсхолдеры `{0}`, разметка `<b>`, обрывы
5. Раскладка по корзинам:

```
принято        → langs/ru/data/
устарело       → strName отсутствует в текущей игре, в отчёт
подозрительно  → не прошло валидатор, в карантин на ручную вычитку
```

Ничего не применяется молча.

Отдельно: `old/BepInEx/plugins/rus_phrases.json` (560 пар вычитанного человеком UI-текста)
импортируется в UI-слой через сопоставление с каталогом, с той же валидацией.

## Валидатор

Гоняется при сборке, падает при:

- дубликате ключа между файлами `ui/`
- ключе из `catalog/`, отсутствующем в `en`
- расхождении плейсхолдеров между `en` и переводом (`{0} of the {1}` → только `{0}`)
- потере грамматических токенов `[us]`/`[them]`
- сломанной разметке, незакрытых тегах
- отсутствии обязательной категории множественного числа для языка
- превышении `maxLen` для ключа с ограничением
- записи оверлея, чей `strName` отсутствует в текущих данных игры (сирота)

Предупреждения без блокировки: рост короткой строки более чем в полтора раза,
перевод идентичен оригиналу (вероятно, забыт).

Именно этого контроля не было у старого перевода: regex портил строки молча, и узнавали
об этом уже в игре.

## Стратегия проверки

Транспайлер модифицирует ~100–150 методов. Сличение скриншотов глазами для такого объёма
не является методом проверки.

| Уровень | Что проверяет | Когда |
|---|---|---|
| Валидатор | целостность данных перевода | сборка |
| Стартовый self-check | применённых подстановок против ожидаемых по каталогу | каждый запуск |
| Отчёт о дрейфе | литералы и пути, разошедшиеся с каталогом | каждый запуск |
| Псевдоязык `qa` | непокрытый текст на экране | ручной прогон |
| Детектор переполнения | не влезающие переводы | режим `qa` |
| Дымовой прогон | счётчик видимого английского по основным экранам | перед релизом |

Стартовый self-check — основная защита: если применено 140 подстановок из 150 ожидаемых,
это видно в логе сразу, без запуска игры до соответствующего экрана.

Механизм дампа отображаемого текста сохраняется, но переводится из продакшена в роль
**тестового оракула**: он больше не переводит, а измеряет покрытие.

## Пакет для разработчиков

```
ostranauts-i18n/
├── README.md            что это, как проверить за 5 минут
├── SPEC.md              архитектура, форматы, контракты
├── MIGRATION.md         пошаговое внедрение
├── src/                 референсные C# исходники
│   ├── I18n.cs  LocalizedText.cs  LanguagePack.cs  PackLoader.cs
│   └── Grammar/         движок подстановки [us]/[them]/[verb]
├── editor/
│   └── ApplyBindings.cs Editor-скрипт: вешает LocalizedText по catalog/prefabs.json
├── catalog/             каталоги извлечения
├── langs/               готовые en + ru
├── patches/formats.md   270 мест композиции: файл, строка, что → на что
└── tools/               извлечение, валидация, сборка
```

`editor/ApplyBindings.cs` делает внедрение дешёвым: без него нужно вручную повесить
компонент на ~1250 объектов.

`src/Grammar/` — основная ценность пакета: русская модель (6 форм глагола, согласование по
роду, падежи) вместо английской двухформенной. Отдаётся работающей и проверенной на живых NPC.

### Порядок внедрения

| Шаг | Объём | Автоматизация |
|---|---|---|
| 1. Положить `src/` в проект | — | — |
| 2. Прогнать `ApplyBindings.cs` | ~1250 объектов | полная |
| 3. Заменить литералы на `GetString` | 296 мест | список готов, замена механическая |
| 4. Применить формат-строки | 270 мест | diff готов, нужна проверка человеком |
| 5. Положить `langs/` в StreamingAssets | — | — |
| 6. Удалить BepInEx-плагин | — | плагин больше не нужен |

Шаг 6 — критерий успеха. Правильно выполненная работа заканчивается тем, что мод становится
не нужен. Если после внедрения плагин всё ещё требуется, построен очередной костыль.

## Риски

**Неприятие разработчиками.** Транспайлер сложнее в поддержке, чем привязка по пути, и
оправдан в первую очередь соответствием 1:1 с правкой их исходников. Если пакет не будет
принят, мы остаёмся с более тяжёлым модом, чем требовалось бы для одного лишь русского.
Смягчение: мод самодостаточен и работоспособен независимо от решения разработчиков, а
каталоги и грамматический движок сохраняют ценность в любом случае.

**Стоимость старта.** Патч ~100–150 методов транспайлерами удлиняет запуск. Величина
неизвестна до реализации; замеряется на первом рабочем прототипе. При неприемлемом
результате запасной вариант — кеш результатов патча между запусками.

**Объём вычитки каталога.** Автоматически сгенерированные ключи и классификация
«статика / композиция / данные» требуют человеческой проверки на ~1500 записях UI.
Это основная ручная работа проекта.

## Границы v1

Входит:

- UI-слой целиком: `GetString`, литералы в коде, префабы (сцены и шаблоны)
- Множественные числа, шрифтовые цепочки на язык
- Контент-слой: оверлей по `strName`, импорт старого перевода с валидацией
- Смена языка без перезапуска для UI
- Каталоги, валидатор, псевдоязык, детектор переполнения, детект дрейфа
- Пакет для разработчиков

Не входит:

- Локализация форматов чисел и дат (вид D) — назван как задел
- Расширение грамматики до полного MorphContext (падежи `[us:gen]`) — текущая модель работает
- Смена языка контента без перезапуска
- RTL-языки (арабский, иврит) — требуют отдельной работы по вёрстке
- Выполнение самого перевода 13 295 строк контента — строится пайплайн, объём выполняется отдельно

## Открытые вопросы

- Точное число методов под транспайлер измеряется при извлечении каталога; оценка ~100–150.
- Доля литералов в сгенерированных компилятором классах (итераторы, `<>c__DisplayClass`):
  лямбд с UI-текстом найдена одна, но 59 файлов содержат и `IEnumerator`, и присваивание
  `.text`. Требует замера при извлечении: имена таких классов менее стабильны между сборками.
